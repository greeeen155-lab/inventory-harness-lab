# 03. 사용 시나리오

> Phase 3 · 기준: `01-requirements.md`, `02-personas.md`  
> P1 = 물류창고 담당자(폰, 하루 여러 번)  
> P2 = 영업 담당자(PC, 드물게)

---

## 0. 먼저 이해해야 할 전체 흐름

이 앱에서 재고는 기본적으로 **사라지는 것이 아니라 장소를 이동한다.**

```text
[외부]
  ↓ 입고
[자사창고]
  ├─ 판매·납품 ─────────────→ [외부]
  │
  ├─ 풀필먼트 발송 → [배송 중] → [풀필먼트]
  │                              ↓
  │                         고객 출고
  │
  └─ 팝업 반출 ─────────────→ [팝업]
                                 ↓ 행사 종료
                         ┌───────┴───────┐
                       판매            남은 재고
                        ↓                 ↓
                     [외부]          [자사창고]
```

따라서 사용 시나리오는 크게 5개 업무 흐름으로 나뉜다.

1. **창고 입출고** — 물건이 들어오거나 바로 나간다
    
2. **풀필먼트 관리** — 물건을 보내고, 도착시키고, 이후 출고량을 반영한다
    
3. **팝업 관리** — 계획하고, 반출하고, 필요하면 추가 반출하고, 마지막에 정산한다
    
4. **재고 조회** — 지금 실제로 판매 가능한 수량을 확인한다
    
5. **유통기한 관리** — 임박 재고를 먼저 출고하고 만료 재고를 폐기한다
    

---

# A. 창고 입출고

## S1. 입고 — 유통기한이 섞인 박스가 도착했다

### 상황

**P1 / 창고 / 폰 / 물건을 세면서 실시간**

택배가 도착했다.

같은 상품이라도 박스마다 유통기한이 다를 수 있다.

예:

```text
샘플크림
├─ 2026-11-30 / 15개
└─ 2027-03-31 / 30개
```

이것은 예외 상황이 아니라 평소에도 자주 발생한다.

### 흐름

1. 홈 → `입고`
    
2. 상품 검색 → 선택
    
3. 유통기한 + 수량 입력
    
4. 같은 상품에 다른 유통기한이 있으면 `+ 유통기한 추가`
    
5. 저장
    
6. 저장 직후 상품 검색 상태로 돌아감
    
7. 다음 상품 반복
    

하단에는 `오늘 입고한 N건`을 표시한다.

### 저장 후

```text
자사창고

샘플크림
├─ 2026-11-30 / 15개
└─ 2027-03-31 / 30개
```

### 설계 포인트

- 한 상품에 유통기한 여러 개를 한 번에 입력할 수 있어야 한다.
    
- 저장 후 별도의 완료 화면을 보여주지 않는다.
    
- 방금 입력한 건은 바로 수정하거나 취소할 수 있어야 한다.
    
- 창고에서 계속 물건을 세고 있으므로 **연속 입력 속도**가 가장 중요하다.
    

---

## S2. 자사창고 출고 — 지금 물건이 나간다

### 상황

**P1 / 창고 / 폰 / 하루 여러 번**

거래처 납품이나 직접 발송 때문에 자사창고에서 물건을 뺀다.

예를 들어 같은 상품이 다음처럼 있다.

```text
2026-11-30 / 15개
2027-03-31 / 50개
```

20개를 출고해야 한다.

### 흐름

1. 홈 → `출고`
    
2. 상품 검색
    
3. 출고 수량 `20개` 입력
    
4. 앱이 FEFO 기준으로 자동 배분
    

```text
출고 예정

2026-11-30분 15개
2027-03-31분  5개

총 20개
```

5. 저장
    

### 핵심

사용자가 직접 유통기한별 수량을 계산하지 않는다.

앱이 **가장 빨리 만료되는 재고부터 자동으로 선택**한다.

다른 로트를 사용해야 하는 특별한 상황에서만 `변경`을 눌러 수동 선택하고 사유를 입력한다.

# B. 풀필먼트 관리

풀필먼트 업무는 하나의 연결된 흐름이다.

```text
자사창고
   ↓ 발송
배송 중
   ↓ 도착 확인
풀필먼트
   ↓ 고객 주문 출고
풀필먼트 재고 차감
```

---

## S3. 자사창고 → 풀필먼트 발송

### 상황

**P1 / 창고 / 폰 또는 PC / 주기적**

풀필먼트 A에 보낼 상품 5~10종을 박스에 담는다.

### 흐름

1. `풀필먼트 발송`
    
2. 도착 거점 선택
    

```text
도착: 풀필먼트 A
```

3. 여러 상품과 수량을 발송 목록에 추가
    
4. 로트는 **LEFO 기준**으로 앱이 자동 선택 — 유통기한이 **넉넉한 것부터** 보낸다
    
5. `발송 확정`
    

### 발송 전

```text
자사창고 100
배송 중   0
풀필먼트  0

총 재고 100
```

### 발송 후 30개를 보냈다면

```text
자사창고  70
배송 중   30
풀필먼트   0

총 재고 100
```

물건은 없어지지 않았다.

단지 **자사창고 → 배송 중**으로 위치가 바뀌었다.

### 왜 발송만 반대인가

풀필먼트 입고는 **평균 3~5일** 걸리고, 도착한 뒤 고객 주문으로 나가기까지 시간이 더 걸린다.

```text
자사창고에서 직접 판매      →  오늘 나간다
풀필먼트로 보내서 판매      →  3~5일 이동 + 판매 대기
```

여기에 임박한 재고를 보내면 팔리기 전에 기한이 지나 **그대로 폐기**된다.
그래서 발송은 유통기한이 **넉넉한 로트부터** 고르고, 임박분은 자사창고에 남겨 직접 소진한다.

```text
자사창고 보유
  2026-09-10 (23일 남음)  18개  ← 남긴다. 직접 판매로 소진
  2027-03-31 (7개월)      60개  ← 이걸 보낸다

40개 발송 → 2027-03-31에서 40개
```

넉넉한 재고가 모자랄 때만 임박분이 섞이고, 그때는 화면에 경고가 뜬다.

### 설계 포인트

- 발송 목록은 여러 SKU를 한 번에 담는다.
    
- 작성 중 임시 저장이 가능해야 한다.
    
- 발송했다고 바로 풀필먼트 재고로 잡지 않는다.
    
- **배분 방향이 출고와 반대다.** 같은 상품이라도 출고하면 임박분이, 발송하면 넉넉한 분이 나간다.

## S4. 풀필먼트 도착 확인

### 상황

**P1 / 어디서든 / 폰 / 발송 3~5일 후**

풀필먼트사에서 입고 완료 문자가 온다.

예:

```text
풀필먼트 A
입고 완료

샘플크림 30개
```

### 흐름

1. 홈에서 배송 중 건 확인
    

```text
배송 중 3건

풀필먼트 A
4일 경과
```

2. 해당 발송 건 열기
    
3. 발송 당시 목록 확인
    
4. 수량이 같으면 `전량 도착 확인`
    

### 처리 결과

```text
도착 전

자사창고 70
배송 중  30
풀필먼트  0
```

↓

```text
도착 후

자사창고 70
배송 중   0
풀필먼트 30
```

총재고는 계속 100이다.

### 수량이 다르면

예:

```text
우리가 보낸 수량: 30
실제 입고 수량:   29
차이:              -1
```

실제 도착 수량으로 수정하고 차이는 조정 기록으로 남긴다.

### 설계 포인트

- 배송에 3~5일 걸리는 것은 정상이다.
    
- 7일 이상 도착 확인이 없을 때부터 경고한다.
    
- 도착 확인 전까지 해당 재고는 계속 `배송 중`에 존재한다.

## S5. 풀필먼트에서 어제 출고된 수량 반영

### 상황

**P1 / 사무실 또는 폰 / 매일 1회**

풀필먼트에 들어간 물건은 이후 고객 주문에 따라 계속 출고된다.

MVP에서는 풀필먼트 API와 자동 연동하지 않는다.

따라서 P1이 각 풀필먼트 관리자 페이지를 확인하고 **어제 출고된 수량을 우리 앱에 옮겨 적는다.**

### 예시

앱상 풀필먼트 A 재고:

```text
샘플크림 100개
```

어제 풀필먼트에서 고객에게:

```text
7개 출고
```

앱에 `7`을 입력하면:

```text
풀필먼트 A

100 → 93개
```

### 흐름

1. 홈 알림 확인
    

```text
풀필먼트 A
마지막 반영 2일 전
```

2. `풀필먼트 출고 입력`
    
3. 거점 선택
    
4. 상품 목록을 표로 표시
    

|상품|어제 출고|
|---|--:|
|샘플크림|7|
|샘플토너||
|샘플세럼|3|

5. 출고된 상품의 수량만 입력
    
6. 로트는 FEFO로 자동 차감
    
7. 한 번에 저장
    
8. `마지막 반영일` 갱신
    

### 설계 포인트

상품을 하나씩 검색하게 만들지 않는다.

```text
3개 풀필먼트 × 10 SKU
= 매일 최대 30번 검색
```

이 작업은 반복 빈도가 높으므로 **표 형태 일괄 입력**이 기본이다.

`마지막 반영일`은 단순 날짜가 아니라 해당 풀필먼트 재고 숫자의 **신뢰도**를 의미한다.

# C. 팝업 관리

팝업 업무 역시 하나의 연결된 흐름이다.

```text
반출 계획
   ↓
실제 반출
   ↓
팝업 진행
   ↓
필요하면 추가 반출
   ↓
행사 종료
   ↓
남은 실물 수량 입력
   ↓
판매량 자동 계산
   ↓
남은 재고 자사창고 복귀
```

---

## S6. 팝업 준비 — 반출서를 만든다

### 상황

**P2 기획 / PC / 행사 며칠 전**

영업 담당자가 행사에 가져갈 상품을 미리 계획한다.

### 흐름

1. `팝업 만들기`
    
2. 이름·기간 입력
    

```text
성수 팝업
2026.10.10 ~ 2026.10.12
```

3. 팝업 전용 거점 자동 생성
    
4. 반출서 작성
    

|상품|예정 수량|
|---|--:|
|샘플크림|50|
|샘플토너|30|
|샘플세럼|20|

### 중요

이 단계에서는 **재고가 움직이지 않는다.**

반출서는 어디까지나 계획이다.

```text
반출서 작성
≠
실제 재고 반출
```

---

## S7. 실제 팝업 반출

### 상황

**P1 / 창고 / 행사 직전**

창고 담당자가 P2가 작성한 반출서를 보고 실제 물건을 꺼낸다.

### 흐름

1. 반출서 열기
    
2. 예정 수량 확인
    
3. 실제 꺼낸 수량 입력
    
4. 예정과 실제 차이 확인
    
5. `반출 확정`
    

### 예시

```text
예정 50
실제 45

차이 -5
```

재고 부족 등의 이유로 계획과 실제 수량이 다를 수 있다.

### 확정 후

```text
자사창고 -45
팝업     +45
```

로트는 FEFO 기준으로 자동 선택한다.

---

## S8. 행사 중 추가 반출

### 상황

**P1 / 창고 / 행사 기간 중**

예상보다 상품이 잘 팔려 추가로 물건을 보낸다.

### 예시

```text
1차 반출 120개
2차 반출  40개

누적 반출 160개
```

### 흐름

1. 진행 중 팝업 열기
    
2. `추가 반출`
    
3. 상품·수량 입력
    
4. 확정
    
5. 누적 반출 수량 갱신
    

### 핵심

팝업은 한 번 작성하고 끝나는 문서가 아니다.

**여러 번 재고가 들어갔다가 마지막에 정산되는 임시 거점**이다.

따라서 정산 기준은 항상 `최초 반출`이 아니라 **누적 반출**이다.

---

## S9. 팝업 종료 — 남은 물건으로 판매량을 역산한다

### 상황

**P2 또는 P1 / 사무실 PC / 행사 복귀 직후**

팝업 현장에서는 판매할 때마다 앱에 기록하지 않는다.

행사가 끝난 후 남은 박스를 가져와 실물 수량을 센다.

### 예시

팝업에 총 가져간 수량:

```text
누적 반출 160개
```

행사 종료 후 남은 수량:

```text
47개
```

앱 계산:

```text
160 - 47 = 113
```

앱은 확정 전에 사람 말로 보여준다.

> 160개를 반출했고 47개가 돌아왔습니다.  
> 113개를 판매된 수량으로 기록합니다.

### 흐름

1. 팝업 → `정산 시작`
    
2. 반출했던 상품 전체 표시
    
3. 각 상품의 남은 실물 수량 입력
    
4. 유통기한이 여러 개면 로트별 잔여 수량 입력
    
5. 판매량 자동 역산
    
6. 계산 결과 확인
    
7. `정산 확정`
    

### 확정 후

```text
누적 반출 160

├─ 판매 113 → 출고 처리
└─ 잔여  47 → 자사창고 복귀
```

팝업 거점:

```text
재고 0
상태: 종료
```

### 결과 요약

```text
반출 160
판매 113
반입  47
소진율 71%
```

### 설계 포인트

- P2는 앱 사용 빈도가 낮으므로 계산 결과를 사람이 이해할 수 있는 문장으로 확인시킨다.
    
- 정산 확정 후에도 실물 카운트 오류를 발견할 수 있으므로 되돌리기가 가능해야 한다.
    
- 시식·증정을 판매와 구분해야 한다면 정산 단계에서 차감 사유를 선택적으로 기록한다.

# D. 재고 조회

## S10. "이 상품 지금 몇 개 팔 수 있어요?"

### 상황

**P2 / 사무실 PC / 거래처와 통화·메신저 중**

거래처에서 묻는다.

> 샘플크림 지금 300개 가능해요?

P2는 몇 초 안에 답해야 한다.

### 중요한 차이

전체 재고와 **지금 출고 가능한 재고**는 다르다.

예:

```text
자사창고       120
풀필먼트 A     150
풀필먼트 B      70
배송 중         40
팝업 보유       60
─────────────────
전체 재고       440
```

하지만 지금 판매 가능한 수량은:

```text
120 + 150 + 70 = 340
```

따라서 대표 숫자는:

# 지금 출고 가능 340개

그 아래에 거점별 수량을 보여준다.

```text
자사창고      120
풀필먼트 A    150 · 오늘 기준
풀필먼트 B     70 · 2일 전 기준

별도 재고
배송 중        40
팝업 보유      60
```

### 설계 포인트

- 대표 숫자는 `전체 재고`가 아니라 `가용 재고`
    
- 배송 중·팝업 보유는 가용 재고에서 제외
    
- 풀필먼트 재고에는 반드시 `마지막 반영일` 표시
    
- P2는 상품명을 검색해서 바로 답을 얻을 수 있어야 한다.

# E. 유통기한 관리

## S11. 유통기한 임박 재고 확인

### 상황

**P1 / 아침 홈 화면**

홈에 다음 알림이 표시된다.

```text
유통기한 임박 3건
만료 1건
```

### 아직 판매 가능한 재고

예:

```text
샘플크림
풀필먼트 A
2026-09-10
30개
23일 남음
```

별도의 처리 버튼을 누를 필요는 없다.

다음 출고 때 FEFO가 자동으로 이 재고부터 사용한다.

즉 임박 알림의 목적은:

```text
"버리세요"
```

가 아니라:

```text
"이 재고를 먼저 밀어낼 시간이 얼마 남지 않았습니다."
```

라는 신호다.

---

## S12. 만료 재고 폐기

유통기한이 지났다고 앱이 자동으로 재고를 없애지 않는다.

### 흐름

1. 만료 재고 확인
    
2. 실제 물건 확인
    
3. `폐기 처리`
    
4. 사유 입력
    
5. 확정
    

### 처리 전

```text
자사창고
샘플크림 10개
```

### 처리 후

```text
자사창고 0
폐기    10
```

즉 재고가 삭제된 것이 아니라:

```text
자사창고 → 폐기
```

로 이동한 것이다.

이 이동 역시 이력에 남는다.

# 4. 사용자별 핵심 업무

## P1. 물류창고 담당자

P1은 하루에도 여러 번 앱을 사용한다.

핵심 업무:

```text
입고
출고
풀필먼트 발송
도착 확인
풀필먼트 출고량 반영
팝업 실제 반출
추가 반출
유통기한 관리
```

P1 화면의 최우선 기준은 **속도**다.

- 모바일 우선
    
- 한 손 조작
    
- 최소 탭
    
- 저장 후 바로 다음 작업
    
- FEFO 자동 처리
    
- 잘못 입력했을 때 빠른 취소
    

---

## P2. 영업 담당자

P2는 앱을 자주 사용하지 않는다.

핵심 업무:

```text
재고 검색
팝업 생성
반출 계획
팝업 정산
결과 확인
```

P2 화면의 최우선 기준은 **이해하기 쉬움**이다.

따라서 전문 용어보다 결과를 보여준다.

예:

```text
Lot / FEFO
```

보다

```text
지금 출고 가능 340개
```

가 먼저 보여야 한다.

자동 계산 역시 숫자만 보여주지 않는다.

```text
160 - 47 = 113
```

보다

```text
160개를 가져갔고
47개가 돌아왔으므로
113개를 판매된 수량으로 기록합니다.
```

처럼 설명한다.

# 7. 한 줄 요약

이 앱은 단순히 **"재고가 몇 개 있는지 기록하는 앱"**이 아니다.

**상품이 지금 어디에 있고, 어떤 유통기한의 재고가 먼저 나가야 하며, 창고 → 배송 중 → 풀필먼트 또는 창고 → 팝업 → 판매/복귀로 어떻게 이동했는지를 추적하는 앱**이다.

사용자는 이 복잡한 이동 구조를 직접 관리하지 않는다.

- P1에게는 **빠른 입력과 자동 FEFO**
    
- P2에게는 **가용 재고와 이해하기 쉬운 정산 결과**
    

를 보여주는 것이 핵심이다.

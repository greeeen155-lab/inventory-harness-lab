## 1. 프로젝트 정의

**여러 재고 거점(풀필먼트 3사 + 자사 창고 1곳)에 흩어진 재고를 유통기한 기준 선입선출(FEFO)로 관리하고, 오프라인 팝업 반출·반입까지 추적하는 사내 재고관리 앱**

| 항목 | 결정 |
|---|---|
| 목적 | 팀 내부 실사용 (PoC지만 실제 재고를 넣고 굴린다) |
| 사용자 | 2~3명, 각자 기기에서 접속 |
| 디바이스 | **모바일 우선**, 데스크톱 병행 |
| 스택 | Next.js (App Router) + TypeScript |
| DB | SQLite (서버 1대에 배치, 공유 접근) |
| 인증 | 로그인 필요 + 변경 이력(누가·언제·무엇을) |

### 이 앱이 푸는 문제
1. 재고가 4곳에 흩어져 **전체 수량을 한눈에 볼 수 없다**
2. 유통기한이 다른 재고가 섞여 **오래된 것부터 나가는지 보장이 안 된다**
3. 팝업 반출은 판매가 아니라 **위치 이동 + 부분 판매**인데, 일반 재고 흐름으로는 표현이 안 된다

## 2. 핵심 개념 — 재고를 세는 단위

### Lot = SKU × 거점 × 유통기한

재고의 최소 단위는 **로트(Lot)**이며, `상품 + 거점 + 유통기한` 세 값이 같으면 하나의 로트로 합쳐진다.

```
로트 예시
  샘플크림 50ml / 자사창고 / 2027-03-31 → 120개
  샘플크림 50ml / 풀필먼트A / 2027-03-31 →  80개   ← 거점이 다르므로 별도 로트
  샘플크림 50ml / 자사창고 / 2026-11-30 →  15개   ← 유통기한이 다르므로 별도 로트
```

- 입고 배치(로트번호) 단위로는 쪼개지 **않는다**. 같은 유통기한이면 같은 물건으로 본다.
- 이유: FEFO는 유통기한 순서만 지키면 충족되고, 입고 건별로 쪼개면 로트가 파편화되어 현장에서 세기 어려워진다.
- 대가: "몇 월 며칠 입고분만 리콜" 같은 추적은 불가능하다. (→ Out of Scope)

### 거점(Location) 5종

| 유형 | 예시 | 성격 |
|---|---|---|
| 자사 창고 | 자사창고 | 우리가 직접 세는 곳. 모든 이동의 출발점 |
| 풀필먼트 | 풀필먼트 A / B / C | 남이 세는 곳. **저쪽 수치가 진실** |
| 팝업 (임시) | 성수 팝업 10월 | 행사 기간에만 존재. 종료 시 잔여 재고 0 |
| 배송 중 | (가상 거점) | 자사창고를 떠났으나 풀필먼트에 아직 안 잡힌 재고 |
| 폐기 | (가상 거점) | 기한 만료로 사람이 확정해 뺀 재고 |

> **배송 중·폐기를 거점으로 두는 이유**: 재고가 "사라지는" 상태를 만들지 않기 위해서다. 모든 수량 변화는 어딘가에서 어딘가로의 이동으로 기록되며, 그래야 총량이 맞는지 검증할 수 있다.

## 3. 기능 요구사항

### F1. 상품(SKU) 관리
- SKU 코드, 상품명, 단위, **유통기한 경고 임계일(품목마다 다름)**
- 상품별 임계일 기본값 제공(예: 60일), 개별 수정 가능

### F2. 거점 관리
- 거점 추가/수정 (유형: 자사창고 / 풀필먼트 / 팝업 / 시스템)
- 팝업 거점은 행사 단위로 생성되고 종료 후 비활성화

### F3. 재고 현황 조회 — 앱의 첫 화면
- **SKU별 전체 수량** + 거점별 분해 (접었다 펼치기)
- **유통기한 임박 재고 강조** (임계일 이내 / 이미 만료)
- 검색·필터: SKU명, 거점, 임박 여부

### F4. 입고
- 자사창고 입고: 상품 + 유통기한 + 수량 → 로트 생성 또는 기존 로트에 합산
- 풀필먼트 직입고도 동일하게 기록 가능

### F5. 출고 (판매·발송)
- **출고 사유를 반드시 남긴다** (기본값 `판매`, 아래 F5-1 참조)
- **FEFO 강제**: 출고 시 유통기한이 가장 임박한 로트를 자동 선택 (외부로 나가는 모든 감소에 적용)
- 다른 로트를 선택하려면 **사유 입력 필수** (예: "고객 요청", "임박분 물류 미도착")
- 수량이 여러 로트에 걸치면 임박 순으로 자동 배분하여 제안

### F5-1. 재고 증감 사유 체계 (표준)

재고가 줄거나 느는 모든 기록에는 사유가 붙는다. 사유별 집계가 있어야 실사에서 차이가 났을 때 원인을 짚을 수 있다.

#### 감소 (재고가 외부로 나감)

| 코드 | 이름 | 설명 | 쓰이는 곳 |
|---|---|---|---|
| `SALE` | 판매 | **기본값.** 거래처 납품·자사몰·풀필먼트 고객 출고 | 출고, 풀필먼트 일일 반영, 팝업 정산 |
| `SAMPLE` | 시식·증정 | 대가 없이 나간 것 (샘플, 시식, 인플루언서 발송) | 출고, 팝업 정산 |
| `DAMAGE` | 파손 | 물리적 손상으로 판매 불가 | 출고, 조정 |
| `LOSS` | 분실 | 행방 불명. 대개 실사에서 발견된다 | 출고, 조정 |
| `DISPOSE` | 폐기 | 유통기한 만료 (F9에서만) | 폐기 처리 |
| `OTHER` | 기타 | **메모 입력 필수** | 전체 |

#### 증가 (재고가 외부에서 들어옴)

| 코드 | 이름 | 설명 | 쓰이는 곳 |
|---|---|---|---|
| `PURCHASE` | 입고 | **기본값.** 매입·생산 입고 | 입고 |
| `RETURN` | 반품 재입고 | 고객·거래처에서 돌아온 물건. 어느 박스가 왔는지 모르므로 **유통기한을 다시 입력**한다 | 입고 |
| `OTHER` | 기타 | **메모 입력 필수** | 입고, 조정 |

#### 조정 전용 (양방향)

| 코드 | 이름 | 설명 |
|---|---|---|
| `COUNT_DIFF` | 대조 차이 | 실사 결과 또는 풀필먼트 수치와의 차이를 반영. **원인 불명이지만 숫자를 맞춰야 할 때** |
| `INPUT_ERROR` | 오입력 정정 | 잘못 입력한 건을 바로잡음 |

> 조정에서 원인이 분명하면 `DAMAGE`·`LOSS`를 쓰고, 모르면 `COUNT_DIFF`를 쓴다. 자사창고에 `COUNT_DIFF`가 자주 쌓인다면 창고 관리에 구멍이 있다는 신호다.

#### 사유가 붙지 않는 것 — 위치 이동

아래는 재고가 늘거나 주는 게 아니라 **장소만 바뀌는 것**이므로 사유 체계를 쓰지 않는다. 총 재고는 변하지 않는다.

| 이동 | 경로 |
|---|---|
| 풀필먼트 발송 | 자사창고 → 배송 중 |
| 도착 확인 | 배송 중 → 풀필먼트 |
| 팝업 반출 (추가 반출 포함) | 자사창고 → 팝업 |
| **팝업 복귀** | **팝업 → 자사창고** |

> **팝업에서 돌아온 물건은 반품이 아니다.** 반품은 외부에 나갔던 물건이 우리 재고로 새로 들어오는 것이고, 팝업 복귀는 우리 재고가 자기 자리로 돌아오는 것이다. 유통기한도 반출 기록에 남아 있어 다시 물을 필요가 없다.
> 팝업 정산에서 사유가 붙는 대상은 **돌아오지 않은 수량뿐**이다 (판매 또는 시식·증정).

#### 규칙
- 사유는 화면에서 **기본값이 미리 선택**되어 있고, 바꿀 때만 손이 간다 (S1·S2의 3탭 원칙)
- `OTHER`는 메모 없이 저장할 수 없다
- 판매처(거래처명·판매 채널) 구분은 **하지 않는다** → Out of Scope

### F6. 거점 간 이동 (자사창고 → 풀필먼트, 빈번)

> **★ 배분 방향이 출고와 반대다 (LEFO)**
> 풀필먼트는 **도착까지 3~5일**, 도착 후 고객에게 나가기까지 더 걸린다.
> 여기에 임박한 재고를 보내면 팔리기 전에 기한이 지나 그대로 폐기된다.
> 따라서 **발송은 유통기한이 넉넉한 로트부터** 고른다.
> 임박분은 자사창고에 남겨 직접 판매·납품으로 빠르게 소진한다.
>
> | 동작 | 배분 | 이유 |
> |---|---|---|
> | 출고(판매·시식·파손) | **FEFO** 임박분 먼저 | 곧 소비되므로 임박분부터 내보내야 안 버린다 |
> | 풀필먼트 일일 반영 | **FEFO** 임박분 먼저 | 이미 고객에게 나간 물량을 차감하는 것 |
> | 팝업 반출 | **FEFO** 임박분 먼저 | 현장에서 며칠 안에 팔리므로 밀어내기 좋다 *(실무도 이렇게 한다 — 2026-08-18 확인)* |
> | **풀필먼트 발송** | **LEFO 넉넉한 분 먼저** | 도착·판매까지 오래 걸린다 |
> | 폐기 | 만료분 지정 | — |
>
> 넉넉한 재고가 모자랄 때만 임박분이 섞이며, 이때 화면에 **⚠ 임박분이 포함됐습니다** 경고를 띄운다.

- 2단계 처리: **발송(출발)** → **입고 확인(도착)**
- 발송 시 재고는 `배송 중` 상태로 이동 (자사창고에서는 빠지지만 총량은 유지)
- 도착 확인 시 목적지 거점 로트로 편입
- 미확인 이동 목록을 별도로 표시 (오래 방치된 건 경고)

### F7. 팝업 반출·반입 — 이 앱의 차별 지점
1. **팝업 생성**: 이름, 기간, 출발 거점(자사창고)
2. **반출**: 상품·로트 선택 → 팝업 거점으로 이동. FEFO 추천 적용
3. **행사 중**: 팝업 거점에 재고가 그대로 잡혀 있음 (판매 건별 기록은 하지 않음)
4. **반입 정산**: 복귀 시 **남은 실물 수량만 입력** → `반출 − 반입 = 판매`로 역산
   - **차감분(반출 − 반입)을 판매와 시식·증정으로 나눠 입력**한다
     - 예: 차감 113개 → 시식·증정 수량 입력(기본 0, 모르면 그대로) → 나머지가 판매
     - 시식 수량이 차감분보다 클 수 없다 (입력 검증)
   - 역산된 판매 수량을 화면에서 확인 후 확정
   - 확정 시: 잔여분은 자사창고로 복귀, 판매분은 출고 처리
   - 로트별로 반입 수량을 입력해야 유통기한 정보가 보존됨
5. **정산 결과 요약**: 반출 / 판매 / 반입 / 소진율

### F8. 재고 조정 (실사) — 필수
- "풀필먼트사 수치가 진실"이라는 원칙의 실행 수단
- 거점·로트별로 **실물 수량 입력** → 장부와의 차이를 표시 → 확정 시 조정 기록 생성
- 조정에는 **사유 입력 필수** — F5-1 체계를 그대로 사용 (`COUNT_DIFF` / `DAMAGE` / `LOSS` / `INPUT_ERROR` / `OTHER`)
- 조정 이력은 삭제 불가

### F9. 유통기한 만료 처리 + 알림
- **자동 폐기는 하지 않는다.** 기한이 지나도 사람이 확정하기 전까지 재고에 남아 있다
- **알림(노티)은 준다** — 앱 안에서 눈에 띄게:
  - 상단 알림 배지: 임박 N건 / 만료 N건 / 폐기 대기 N건
  - 홈 화면 상단 알림 카드에서 해당 로트 목록으로 바로 이동
  - 재고 목록에서 임박·만료 로트는 아이콘 + 텍스트로 구분 (색만으로 구분하지 않음)
- 폐기 확정 시: 폐기 거점으로 이동 + 사유 기록. 이력에 남고 되돌리려면 상쇄 기록 필요
- 알림 채널은 **앱 내 표시만**. 이메일·슬랙·푸시 발송은 v2 (→ Out of Scope)

### F10. 이력 / 감사 로그
- 모든 수량 변화는 이동 기록(Movement)으로 남는다: 언제 · 누가 · 어떤 로트 · 출발지 → 도착지 · 수량 · 사유
- 기록은 **수정·삭제 불가**. 잘못 입력했으면 반대 기록으로 상쇄(취소 기능)
- SKU별 / 거점별 이력 조회

### F11. 로그인
- 이메일 + 비밀번호, 계정은 관리자가 등록 (공개 가입 없음)
- 모든 기록에 작성자가 남는다

## 4. 데이터 모델 (개념)

```
User        id, email, name, password_hash, role
Product     id, sku, name, unit, expiry_alert_days, is_active
Location    id, name, type(OWN|FULFILLMENT|POPUP|TRANSIT|DISPOSAL), is_active
Lot         id, product_id, location_id, expiry_date, quantity
              └ UNIQUE(product_id, location_id, expiry_date)
Movement    id, type(INBOUND|OUTBOUND|TRANSFER|POPUP_OUT|POPUP_IN|ADJUST|DISPOSE)
              reason,   ← F5-1의 사유 코드. 이동(TRANSFER/POPUP_*)에는 null
              product_id, expiry_date, quantity,
              from_location_id, to_location_id,   ← null이면 외부(입고/출고)
              note, popup_id, transfer_id, user_id, created_at
Transfer    id, from_location_id, to_location_id, status(SENT|RECEIVED|CANCELLED),
              sent_at, received_at, sent_by, received_by
Popup       id, name, location_id, source_location_id,
              status(PREP|ACTIVE|SETTLING|CLOSED), start_date, end_date
```

**진실의 원천**: `Movement`가 이력의 원본이고, `Lot.quantity`는 그 결과를 빠르게 읽기 위한 현재값이다. 둘은 항상 같은 트랜잭션 안에서 갱신한다.

## 5. 비기능 요구사항

| 구분 | 요구 |
|---|---|
| 데이터 무결성 | 모든 수량 변화는 DB 트랜잭션. **재고가 음수가 되는 입력은 거부** |
| 되돌리기 | 삭제 대신 상쇄 기록. 이력은 불변 |
| 모바일 | 창고·팝업 현장에서 한 손 조작. 숫자 입력은 큰 터치 영역, 수량 +/− 버튼 |
| 성능 | SKU 수백~수천 개, 로트 수천 개 기준 목록 조회 1초 이내 |
| 한글 입력 | IME 조합 중 검색이 깨지지 않을 것 |
| 접근성 | 임박/만료 표시를 **색만으로 구분하지 않는다** (아이콘·텍스트 병기) |
| 백업 | SQLite 파일 백업 절차를 README에 명시 |
| 알림 | 앱 내 배지·카드로만. 외부 발송(이메일·슬랙) 없음 |
| 오프라인 | **지원하지 않음.** 팝업 현장에서 네트워크가 필요하다 (→ Out of Scope) |

## 7. 완료 기준 (Definition of Done)

아래를 **실제 데이터로** 통과하면 완료로 본다.

1. 로그인한 2명이 각자 폰과 PC에서 접속해 같은 재고를 본다
2. 자사창고에 유통기한이 다른 같은 상품을 2건 입고하면 **로트 2개로 분리**된다
3. 그 상품을 출고하면 **임박한 로트가 먼저 자동 선택**되고, 다른 로트를 고르면 사유를 요구한다
4. 자사창고 → 풀필먼트 이동을 발송하면 `배송 중`에 잡히고, 도착 확인 전까지 **총 재고 수량은 변하지 않는다**
5. 같은 상품을 **출고하면 임박분이, 발송하면 넉넉한 분이** 선택된다 (FEFO ↔ LEFO)
6. 팝업을 만들어 30개 반출 → 18개 반입 정산하면, **차감 12개가 역산**되고, 그중 시식 2개를 입력하면 **판매 10 / 시식 2**로 기록되며 자사창고 재고가 18개 복귀한다
7. 파손 3개를 사유와 함께 출고하면 재고가 줄고, **사유별 집계에서 판매와 분리되어** 보인다
8. 풀필먼트 재고를 실사 조정하면 차이가 표시되고, **사유 없이는 확정되지 않는다**
9. 임계일 이내 유통기한 로트가 알림에 뜨고, 폐기 확정 전까지 재고에서 빠지지 않는다
10. 모든 화면이 폰 세로 화면에서 가로 스크롤 없이 조작된다
11. 이력 화면에서 위 모든 행위가 **누가·언제** 했는지 확인된다
12. 서버를 재시작해도 데이터가 남아 있다

## 8. 확인이 필요한 가정

문서 작성 중 답변이 없어 아래는 **가정하고 진행**했습니다. 다르면 알려주세요.

1. **확정됨** — `배송 중` 가상 거점 도입, 폐기는 수동 확정 + 앱 내 알림 (2026-08-18 확인)
2. **팝업을 별도 거점으로 모델링** — 행사 기간 중 재고가 "팝업"이라는 장소에 있는 것으로 보입니다. (대안: 자사창고 안의 "반출 중" 상태)
3. **실사(F8)를 MVP에 포함** — "풀필먼트 수치 우선" 원칙상 대조·조정 수단이 없으면 앱이 무의미해지기 때문입니다.
4. **로그인은 관리자가 계정을 심는 방식** — 가입 화면 없음.
5. **실행 환경 확정 (2026-08-18)** — 이 PoC는 **강의·시연용 로컬 실행**이 1차 목적이다. `git clone` → `npm install` → `npm run seed` → `npm run dev`로 목업 데이터가 든 앱이 바로 뜬다. 원격 배포는 이번 범위가 아니다. 따라서 SQLite 파일 영속성 문제는 발생하지 않는다.
6. **풀필먼트 3사의 실제 이름** — 미정이므로 설정 화면에서 거점을 직접 추가하는 방식으로 만듭니다.

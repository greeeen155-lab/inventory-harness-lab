# 02. 페르소나

> Phase 2 · 기준 문서: [01-requirements.md](./01-requirements.md)

사용자는 2~3명뿐이지만 **두 사람의 사용 방식이 정반대**다. 이 앱의 설계 난이도는 기능 수가 아니라 이 둘을 한 앱에 담는 데서 나온다.

---

## P1. 물류창고 담당자 — 주 페르소나

### 프로필
| 항목 | 내용 |
|---|---|
| 역할 | 자사창고 실물 관리, 입고·출고·풀필먼트 발송, 재고 숫자의 최종 책임자 |
| 사용 빈도 | **하루 여러 번**, 입출고가 생길 때마다 그때그때 |
| 디바이스 | **폰** (창고에서 물건을 든 채로), 정리·대조는 PC |
| 현재 도구 | 구글시트 + 풀필먼트 3사 관리자 페이지 각각 |
| 앱 숙련도 | 매일 쓰므로 곧 숙련. 용어(로트, FEFO)를 배울 의향 있음 |

### 목표
1. 물건을 만지는 그 순간에 **10초 안에** 입력을 끝내고 다음 일로 넘어간다
2. "어느 거점에 뭐가 몇 개 남았나"를 시트 4개를 열지 않고 한 화면에서 본다
3. 유통기한 넘겨서 버리는 일을 없앤다
4. 풀필먼트에서 받은 숫자와 우리 숫자를 맞춰 놓는다

### 불만 (현재)
- **시트와 실물이 어긋난다.** 바쁘면 나중에 적으려다 잊는다 → 다음 날 숫자를 못 믿는다
- **유통기한이 시트의 한 칸일 뿐이다.** 정렬해서 보지 않으면 임박한 걸 모른다 (사고 나)
- **풀필먼트 3사 페이지를 각각 열어야** 전체가 보인다 (사고 라와 같은 뿌리)
- 자사창고에서 풀필먼트로 보냈는데 **도착 처리가 언제 됐는지 몰라** 그 사이 재고가 붕 뜬다
- 재고 있는 줄 알고 발송 약속을 했는데 없다 (사고 가)

### 행동 패턴
- 폰을 한 손에 들고, 다른 손엔 박스. **양손 조작·긴 폼·작은 버튼이 전부 장벽**
- 수량은 대개 1, 2, 10, 50 같은 단순한 숫자. 키패드 타이핑보다 **+/− 버튼과 프리셋**이 빠르다
- 같은 상품을 연속으로 여러 건 처리한다 → 입력 후 **다음 입력으로 바로 이어지는** 흐름이 필요
- 유통기한은 박스에 인쇄돼 있다. 보고 그대로 입력한다 → **날짜 입력이 느리면 여기서 막힌다**

## P2. 영업 담당자 — 대조 페르소나

### 프로필
| 항목 | 내용 |
|---|---|
| 역할 | 판매·거래처 대응, **오프라인 팝업 기획과 진행** |
| 사용 빈도 | **드물게.** 팝업 전후로 몰아서, 평소엔 "이거 재고 있어요?" 확인용 |
| 디바이스 | **PC** (사무실). 팝업 현장에서는 앱을 쓰지 않음 |
| 앱 숙련도 | **낮게 유지된다.** 2주 만에 열면 지난번 쓰던 법을 잊는다 |

### 목표
1. 거래처·고객 문의에 **재고가 있는지 즉답**한다
2. 팝업에 나갈 물량을 창고 담당자와 맞춰 반출한다
3. 팝업 끝나고 **얼마나 팔렸는지** 숫자로 확인한다

### 불만 (현재)
- 재고를 물어보려면 **창고 담당자에게 물어봐야 한다.** 상대가 바쁘면 답이 늦다
- 팝업 다녀오면 **숫자가 안 맞는다** (사고 다). 판매량이 정확히 얼마인지 아무도 모른 채 넘어간다
- 시식·증정으로 나간 것과 실제 판매가 뒤섞인다

### 행동 패턴
- **검색부터 한다.** 상품명을 치고 "총 몇 개"를 본다. 거점별 분해는 그다음
- 로트·FEFO·배송중 같은 개념을 **모르고, 알고 싶어 하지도 않는다**
- 팝업 반출·반입은 **한 번에 여러 상품**을 처리한다 (한 건씩 찍는 흐름이 맞지 않음)
- 정산은 현장이 아니라 **복귀 후 책상에서**, 종이 메모나 남은 박스를 보며 한다

## 두 페르소나의 긴장 축

| 축 | P1 물류창고 | P2 영업 | 설계에 주는 압력 |
|---|---|---|---|
| 사용 빈도 | 하루 여러 번 | 2주에 한 번 | 속도 최적화 ↔ 학습 없이 쓰기 |
| 디바이스 | 폰, 한 손, 서서 | PC, 앉아서 | 모바일 우선이되 PC에서 초라하지 않게 |
| 작업 단위 | 상품 1건씩 연속 | 여러 상품 한 번에 | 단건 빠른 입력 ↔ 다건 일괄 입력, **둘 다 필요** |
| 보는 단위 | 로트(유통기한별) | SKU 총량 | 기본은 총량, 펼치면 로트 |
| 용어 | 로트·FEFO 이해함 | 모름 | 전문 용어를 화면 전면에 두지 않는다 |
| 실수 비용 | 본인이 바로 알아챔 | **모르고 지나감** | 영업이 만지는 화면은 되돌리기·확인 단계가 더 필요 |
| 관심사 | 정확성 | 결과(얼마 팔렸나) | 팝업 정산 끝에 **요약 화면**이 있어야 함 |

## 도출된 설계 긴장점

**T1. 하루 여러 번 vs 2주에 한 번 — 같은 화면이 둘 다 만족시킬 수 없다**
P1에게 최적인 화면(단축키·최소 확인·전문 용어)은 P2에게 불친절하고, P2에게 최적인 화면(설명·단계별 안내)은 P1에게 느리다.
→ **입출고 흐름은 P1 기준으로 빠르게, 팝업 흐름은 P2 기준으로 친절하게.** 두 흐름을 홈에서 명확히 갈라 놓는다.

**T2. 정확성의 책임이 한 사람(P1)에게만 있다**
P2가 잘못 입력해도 알아채는 건 P1이다. 그런데 P2는 그 사실을 모른다.
→ 팝업 정산처럼 P2가 만지는 확정 행위는 **역산 결과를 사람 말로 보여주고 확인받는다** ("30개 나갔고 18개 돌아왔으니 12개 판매로 기록합니다").

**T3. "그때그때 입력"은 앱이 느린 순간 무너진다**
P1이 지금 시트에 못 적는 이유는 게을러서가 아니라 그 순간 손이 바빠서다. 앱이 시트보다 느리면 똑같이 안 적게 되고, **그 순간 이 앱은 죽는다.**
→ 입고/출고는 **3탭 이내 완료**를 목표로 한다. 이것이 이 앱의 단일 최우선 성능 지표다.

**T4. 사고 (가)(나)(다)가 전부 일어난다 — 홈 화면 자리싸움**
품절, 유통기한 초과 폐기, 팝업 후 불일치가 모두 실제로 발생 중이다. 셋 다 홈에 놓으면 아무것도 안 보인다.
→ 홈은 **① 지금 조치가 필요한 알림(유통기한·미확인 이동) → ② 재고 검색 → ③ 빠른 입출고 버튼** 순서. 팝업은 진행 중일 때만 홈에 뜬다.

**T5. 풀필먼트 숫자는 "옮겨 적는" 것이다 — 실사가 아니라 받아쓰기다**
P1은 풀필먼트 재고를 직접 세지 않는다. 저쪽 숫자를 보고 입력할 뿐이다.
→ 풀필먼트 거점의 조정 화면은 "실사"가 아니라 **"풀필먼트 수치 반영"**이라는 이름과 흐름으로 만든다. 차이는 오류가 아니라 **정상적인 갱신**으로 취급하되, 차이가 큰 건은 눈에 띄게 한다.
→ 반면 자사창고는 직접 세므로 **진짜 실사 흐름**(로트별 실물 카운트)이 맞다. 두 화면은 성격이 다르다.

**T6. 팝업 정산은 현장이 아니라 책상에서 일어난다**
현장 입력을 전제로 만들 필요가 없다. 오히려 **복귀 후 남은 박스를 보며 여러 상품을 한 번에 입력**하는 표 형태가 맞다.
→ 모바일 최적화 압박에서 자유로운 유일한 화면. PC에서 넓게 쓴다.

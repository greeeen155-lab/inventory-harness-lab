# 00. Harness SSOT

> 문서 역할: 요구사항·아키텍처·개별 작업의 권위 있는 원본과 경계를 연결하는 인덱스
> 상태: 초안
> 기준일: 2026-08-26

## 1. 목적과 범위

이 문서는 각 영역의 **SSOT(진실의 원천)** 를 선언하고 서로의 권위 범위를 구분한다. 원본 문서의 내용을 복제하거나, 이 문서 자체를 제품 요구사항·아키텍처·개별 작업의 대체 문서로 사용하지 않는다.

이 문서가 관리하는 범위는 다음과 같다.

- 영역별 권위 원본과 참조 경로
- 원본 간 우선순위와 경계
- 개별 작업의 GitHub Issue 참조 방식
- 원본 충돌을 다루는 방식
- 아직 정의하지 않은 문서 영역의 상태

## 3. 원본 간 우선순위와 경계

원본의 권위는 역할별로 다음과 같이 구분한다.

1. **요구사항 원본** — 제품 의도, 범위, 재고 도메인 정책, 완료 기준
2. **원칙 원본** — 업무 시나리오에서 도출된 설계 원칙
3. **아키텍처 원본** — 요구사항과 원칙을 구현하는 기술 구조와 구현 계약
4. **해당 GitHub Issue** — 위 범위 안에서의 개별 작업, 수용조건, 상태와 논의
5. **참고 문서** — 계획, 현재 상태, 인수인계와 보조 설계 맥락

원칙은 요구사항과 아키텍처를 연결하는 설계 기준이다. 원칙 원본의 내용이 요구사항을 변경하거나 아키텍처 계약을 조용히 덮어쓰지는 않는다.

이 순서는 Issue가 요구사항이나 아키텍처를 조용히 덮어쓸 수 있다는 뜻이 아니다. 상위 원본의 변경이 필요하면 먼저 해당 원본을 승인된 변경으로 갱신하고, 관련 Issue의 범위·수용조건·참조를 동기화한다.

이 문서는 원본의 내용을 재기록하지 않으며, 원본 링크와 권위 경계만 관리한다.

## 4. 원칙 원본

[docs/03-scenarios.md](../03-scenarios.md)의 설계 원칙(P1~P12)을 원칙의 원본으로 삼는다. 이 문서에는 원칙의 내용을 복제하지 않고, 해당 원본과 요구사항·아키텍처의 연결만 기록한다.

원칙이 변경되면 요구사항 및 아키텍처에 미치는 영향을 확인하고, 관련 개별 작업이 있다면 GitHub Issue의 참조와 수용조건을 함께 갱신한다.

### 4.1 원본 관리 원칙

1. 한 영역의 원본은 하나만 둔다.
2. 같은 내용이 여러 곳에 있으면 등록된 원본을 기준으로 판단한다.
3. 원본과 사본의 내용이 다르면 원본은 유지하고 사본을 수정한다.
4. 아직 원본이 없는 영역은 임의의 문서를 기준으로 삼지 않는다.

## 5. 개별 작업 원본: GitHub Issue

### 5.1 작업 참조 규칙

개별 작업 원본의 참조는 다음 규칙에 따른다.

저장소: [greeeen155-lab/inventory-harness-lab](https://github.com/greeeen155-lab/inventory-harness-lab)

모든 개별 구현 작업은 먼저 독립 GitHub Issue를 만들고, 그 Issue를 작업의 원본으로 삼는다.

- canonical URL: `https://github.com/greeeen155-lab/inventory-harness-lab/issues/<number>`
- 식별자: `greeeen155-lab/inventory-harness-lab#<number>`
- Issue 본문과 수용조건이 작업 범위의 원본이다.
- Issue의 상태와 논의는 작업의 진행·결정 맥락의 원본이다.
- PR은 구현·검토·병합 기록이며 작업의 원본이 아니다.
- 문서에는 Issue 내용을 복사하지 않고 번호와 canonical URL, 필요한 참조만 기록한다.
- 아직 Issue가 없는 작업은 등록된 작업처럼 기록하지 않고 `미등록`으로 표시한다.
- 유지보수 작업은 [`.github/ISSUE_TEMPLATE/maintenance.yml`](../../.github/ISSUE_TEMPLATE/maintenance.yml) 양식을 사용해 대상·수치·완료 조건·검증 절차를 명시한다.

### 5.2 작업 참조 레지스트리

2026-08-26 기준 별도 GitHub Issue는 **0개**다. 기존 병합 PR은 Issue 원본으로 소급 등록하지 않는다.

| Issue 참조 | 작업 목표·범위 | 상태 | 수용조건 | 관련 원본 | 비고 |
|---|---|---|---|---|---|
| 현재 등록된 Issue 없음 (`0개`) | 해당 없음 | 미등록 | 해당 없음 | 해당 없음 | 새 작업은 Issue 생성 후 등록 |

향후 작업을 등록할 때는 `#<number>`와 전체 canonical URL을 함께 기록한다. 동일한 번호가 다른 저장소에서 사용될 수 있으므로 `#<number>`만을 원본 식별자로 사용하지 않는다.

## 6. SSOT 충돌 처리 정책

충돌이 발생하면 AI는 자신의 판단만으로 우선순위를 정하거나 작업을 진행하지 않는다.

1. **참고 문서와 SSOT가 충돌하면 SSOT를 우선한다.** 참고 문서는 SSOT에 맞춰 수정 대상으로 표시한다.
2. **GitHub Issue와 SSOT가 충돌하면 `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다.** 사람의 판단이 확정되기 전에는 충돌에 의존하는 작업을 진행하거나 완료 처리하지 않는다.
3. **SSOT와 SSOT가 충돌해도 `NEEDS_HUMAN` 상태를 선언하고 사람에게 판단을 요청한다.** 어느 SSOT가 우선인지 AI가 결정하지 않는다.
4. **AI는 충돌이 발생할 경우 자신의 판단대로 행동하지 않는다.** 충돌 사실과 관련 원본을 명시하고, 사람의 판단 전까지 작업을 보류한다.
5. **사람이 SSOT 수정을 명시적으로 요청하면 그 요청을 받아들인다.** 다만 변경 대상과 내용을 확인한 뒤, 요청받은 범위 안에서만 수정한다.

## 7. 충돌 기록 및 후속 처리

충돌을 발견하면 다음 정보만 기록하고 사람의 판단을 기다린다.

- 충돌한 원본과 해당 절
- 충돌한 내용의 요약
- 영향을 받는 작업 또는 Issue
- 상태: `NEEDS_HUMAN`

사람의 판단이 확정되면 결정된 SSOT를 갱신하고, 관련 참고 문서·Issue·사본의 내용을 그 결정에 맞춰 동기화한다.

## 8. 보호 경로 변경 승인

다음 경로는 SSOT 보호 대상이다.

<!-- protected-paths:start -->
- `AGENTS.md`
- `CLAUDE.md`
<!-- protected-paths:end -->

`docs/harness/00-ssot.md` 자체는 사람이 명시적으로 요청한 SSOT 정책 변경을 반영하는 관리 문서이므로 보호 경로 검사 대상에서 제외한다. SSOT 변경은 이 문서의 충돌 처리 정책과 사람의 요청 범위에 따라 처리한다.

보호 경로 변경 여부만으로 사람의 변경을 차단하지 않는다. `scripts/protected-check.ts`는 신뢰된 AI harness가 제공하는 세션 provenance가 있을 때에만 AI 변경으로 분류하고, 그 provenance에 기록된 명시적 작업 범위를 벗어난 보호 경로 변경을 차단한다.

### 8.1 AI 변경 provenance

사람이 직접 수정한 변경과 일반 Git workflow는 provenance가 없으므로 통과한다. 사람이 AI에게 보호 경로 수정을 명시적으로 지시한 경우에는 AI harness가 세션의 정확한 경로 범위를 provenance로 기록하면 해당 범위 안의 변경을 허용한다.

- provenance는 저장소 밖의 신뢰된 AI harness가 실행 중에 전달하는 일시적 정보다.
- `source`, 세션 식별자, 저장소 식별자, 명시적으로 허용된 exact 경로와 실제 변경 경로를 포함해야 한다.
- `PROTECTED_APPROVED`와 `PROTECTED_APPROVER`는 승인 수단이 아니며 무시한다.
- provenance가 없으면 Git diff만으로 사람과 AI를 구분할 수 없으므로 보호 변경을 이유로 실패시키지 않는다.
- 유효한 AI provenance의 범위를 벗어난 보호 변경은 `NEEDS_HUMAN`으로 실패한다.
- 이 저장소에는 아직 provenance를 생성하는 agent 수정 wrapper가 없으므로, provenance 없는 AI 변경을 자동으로 탐지할 수 있다는 보장은 없다.

AI는 자연어 지시를 임의로 승인 문자열로 변환하지 않는다. 명시적 지시와 exact 범위의 기록은 외부 harness의 책임이며, 검증기는 Git diff만으로 그 사실을 추론하지 않는다.

## 9. 검증·구현 루프 정책

### 9.1 검증 규칙

**원본: [docs/harness/02-verification.md](./02-verification.md)**

변경사항 검증의 대상, 순서, 실행 방법과 판정 기준은 `docs/harness/02-verification.md`를 원본으로 삼는다. 실행 스크립트는 이 원본에 정의된 검증을 수행하는 구현 수단이며, 이 문서에는 개별 검증 절차를 복제하지 않는다.

### 9.2 구현·검증 루프

**원본: [docs/harness/03-loop.md](./03-loop.md)**

Issue를 기준으로 구현·검증·판정·재시도·종료·사람 인계·세션 재개를 진행하는 절차는 `03-loop.md`를 따른다. 이 문서에는 루프의 세부 절차를 복제하지 않는다.

유지보수 Issue의 입력 형식과 `max-loops` 필드는 [`.github/ISSUE_TEMPLATE/maintenance.yml`](../../.github/ISSUE_TEMPLATE/maintenance.yml)을 따른다. 원본 간 충돌 또는 사람 판단이 필요한 경우 이 문서의 충돌 처리 정책을 따른다.

### 9.3 검증과 반복의 경계

- `docs/harness/02-verification.md`는 한 번의 검증 실행과 그 판정만 담당한다.

- 이 문서는 두 원본의 위치와 권위만 연결하며 세부 절차를 복제하지 않는다.

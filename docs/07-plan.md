> Phase 7 · 기준: [05-design.md](./05-design.md), [06-architecture.md](./06-architecture.md)

## 0. 실행 방식 — 수강생 입장

```bash
git clone <repo> && cd inventory_poc
npm install
npm run dev        # dev.db 없으면 자동으로 migrate + seed 후 기동
```

| 대상 | 깃 처리 |
|---|---|
| `prisma/dev.db` | **.gitignore** (바이너리 · 충돌 · 스키마 드리프트) |
| `prisma/migrations/` | 커밋 — 스키마 재현에 필수 |
| `prisma/seed.ts` | 커밋 — 목업 데이터의 원본이자 교재 |
| `scripts/ensure-db.ts` | 커밋 — 첫 실행 시 자동 생성 |

시연 중 데이터가 엉키면 `npm run seed:reset` (5초).

## 1. 마일스톤 개요

| M | 목표 | 끝나면 보이는 것 | 예상 |
|---|---|---|---|
| **M1** | 뼈대 · DB · 시드 | Prisma Studio에 강아지 간식 재고가 보인다 | 1.5h |
| **M2** | 로그인 · 홈 · 상품 상세 | 로그인 후 재고·유통기한·거점을 조회한다 | 1.5h |
| **M3** | 입고 · 출고 (FEFO) | 6자리로 입고하고, 출고 시 임박분이 자동 선택된다 | 2h |
| **M4** | 발송 → 도착 확인 | 배송 중에 잡히고 **총 재고가 변하지 않는다** | 1.5h |

## M1. 뼈대 · DB · 시드 (1.5h)

### 할 일
1. `create-next-app` (TypeScript, App Router, Tailwind)
2. **`lib/constants.ts` 먼저 작성** — `as const` 상수와 파생 타입
   - `LOCATION_TYPES` / `MOVEMENT_TYPES` / `REASON_CODES` / `TRANSFER_STATUS` / `POPUP_STATUS`
   - 문자열 상태값을 DB가 막아주지 않으므로 타입이 1차 방어선
3. `tailwind.config.ts`에 05-design 색상 토큰 이식 (`--acc #5B21B6` 외)
4. `prisma/schema.prisma` 작성 → `prisma migrate dev --name init`
5. `lib/db.ts` — PrismaClient 싱글턴 + `PRAGMA journal_mode = WAL`
6. `prisma/seed.ts` — 06-architecture 7절 설계대로. **로트를 손으로 지정하지 않고 `applyMovement`/`allocateLots`를 통과시키고, 사건을 시간 순서대로 실행한다**
   - 계정 2 · 거점 7 · 상품 8 · 로트(임박 3 · 만료 2 포함)
   - 배송 중 3건(1건은 8일 경과) · 풀필 C 3일 미반영 · 성수 팝업 반출 2회
   - 이력 30건 (두 사용자가 섞여서)
7. `scripts/ensure-db.ts` + `package.json` 스크립트

> **구현 중 변경**: `lib/stock.ts`의 `applyMovement()`와 `lib/fefo.ts`를 M3에서 **M1으로 앞당겼다.**
> 시드 데이터를 같은 함수로 만들어야 Lot 수량과 Movement 이력이 처음부터 어긋나지 않기 때문이다.

### 검증
- **수동**: `npm run db:studio` → Lot 테이블에 유통기한이 다른 로트가 분리되어 보임
- **수동**: `rm -f prisma/dev.db && npm run dev` → 자동 복구되어 기동
- **자동**: 없음 (스키마 단계)

## M3. 입고 · 출고 (FEFO) (2h)

### 할 일
1. `lib/stock.ts` — **`applyMovement()`**. 음수 재고 차단, Lot upsert, Movement 기록을 한 트랜잭션에
2. `lib/fefo.ts` — `allocateFefo()`. 거점 안에서만, 유통기한 오름차순
3. `lib/format.ts` — 6자리 날짜 파싱(`270331` → 2027-03-31, `2703` → 말일), 과거·10년 초과 경고
4. `components/ExpiryKeypad.tsx` — 커스텀 숫자 키패드, 최근 기한 칩, 해석 결과 실시간 표시
5. `app/inbound/page.tsx` + `actions/inbound.ts`
   - `<LocationChip>` 받는 곳(기본 자사창고) + 사유(기본 `PURCHASE`)
   - `＋기한`으로 한 상품에 로트 여러 개
   - 저장 후 **확인창 없이** 상품 검색 상태로 복귀
6. `app/outbound/page.tsx` + `actions/outbound.ts`
   - 거점칩 + 이 거점 보유 수량 표시
   - `<FefoPreview>` — 배분 결과를 날짜 카드로
   - `변경` → 수동 선택 + **사유 필수**

- **수동**: 보유보다 많이 출고 시도 → 저장 버튼 비활성 + 사유 표시

## M6. 팝업 반출 → 정산 (2h)

### 할 일
1. `actions/popup.ts` — 생성 / 반출서 / 반출 확정 / 추가 반출 / 정산 / 정산 취소
2. `app/popups/new/page.tsx` — 팝업 생성 시 **전용 거점 자동 생성**, 반출서 작성(재고 안 움직임)
3. `app/popups/[id]/page.tsx` — **누적 반출** 표시, 추가 반출 진입
4. `app/popups/[id]/settle/page.tsx`
   - ① 반출 로트별 잔여 수량 입력 + 시식·증정 수량 입력(기본 0, 차감분 초과 불가)
   - ② `<SettlementSentence>` — "160개를 가져갔고 42개가 돌아왔습니다…"
   - 확정 → 판매/시식은 외부로, 잔여는 자사창고로 (유통기한 보존)
5. 정산 리포트 (E3) — 반출/판매/시식/반입 KPI + 상품별 소진율 막대 + 안 나간 상품
6. 정산 되돌리기

> **구현 중 결정**
> - 정산 계산은 `src/lib/popup.ts`의 `settlePopupTx()`에 두고 **액션과 테스트가 같은 함수**를 쓴다.
> - 잔여 입력은 **로트별**(유통기한을 보존해야 복귀 로트가 맞는다), 시식·증정은 **상품별**로 받는다.
>   어느 유통기한이 시식으로 나갔는지는 아무도 모르므로 **임박한 로트부터** 시식으로 처리한다.
> - 상태는 `PREP → ACTIVE → CLOSED`만 쓴다. `SETTLING`은 화면이 2단계(입력 → 확인)로 끝나서 필요 없었다.
> - 정산 확정 시 팝업 거점을 비활성화하고(F2), 되돌리면 다시 활성화한다.
> - 누적 집계는 취소(상쇄)된 기록을 제외하고 계산한다 (`liveMovements`).

### 검증
- **수동**: 시드의 성수 팝업(120 + 40 = 160) → 잔여 42, 시식 5 입력 → **판매 113** 역산
- **수동**: 확정 후 팝업 거점 재고 0, 자사창고 +42, 상태 `CLOSED`
- **수동**: 시식 수량을 차감분보다 크게 넣으면 저장 거부
- **자동**: `popup-settle.test.ts` — 누적 기준 역산 / 시식 초과 거부 / 확정 후 총합 일치

## 3. 이번 범위에 넣지 않는 것

Phase 1에서 정한 Out of Scope를 그대로 유지한다.

| 항목 | 비고 |
|---|---|
| 풀필먼트사 API 연동 | 매일 수기 반영으로 대체 (S5) |
| CSV 업로드 대조 | 조정 기능이 같은 역할 |
| 바코드·QR 스캔 | 라벨 체계 전제 필요 |
